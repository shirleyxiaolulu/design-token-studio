## 1. 结论与本次边界

本次应定位为「已上线工作流的增量优化」，不是用新原型重写产品。正式插件已经有两条可用主线：Web JSON 导入，以及现有设计稿反推。保留现有引擎、数据格式和入口，在外层增加更清晰的界面、真实明细、定位、字体更换与操作反馈。

本次审查已完成入口、数据流、消息协议、主要生成/绑定算法、写入边界、回归测试及本地发布包检查。本次仅新增并修订本计划文件，没有修改正式代码、原型、测试或插件 ZIP，也未操作用户的 Figma 设计文件、发布到 GitHub。

- 正式代码基线：`edbb89b`，`Fix opacity variable values for Figma sync`；`package.json` 与插件版本为 2.1.0。

- 本地 `figma-plugin.zip` 内的 `manifest.json`、`code.js`、`ui.html` 与源码逐字节相同。
- 本次执行 `npm test`：基础 49 项、绑定 38 项、预览冒烟 1 项，共 **88 项通过，0 失败**。

**实施原则：先补基线测试，再优化界面，再接真实新增能力。每阶段通过自动测试和对应验收后，才进入下一阶段。**

### 用户确认的冻结范围

- **组件复制是已有能力。**本轮指当前设计稿中的组件复制，沿用现有设计稿复制路径，不重新开发母版复制，不扩展为复制公共组件库母版。对现有行为补回归测试，不等于把它列为待实现功能。
- **保真规则以正式代码为准。**完整保留现有颜色匹配、尺寸取整、字号/圆角/间距分类、阴影保留、模式与透明度规则。原型中的整数阶梯统一、4px 网格吸附、阴影自动合并均不接入本轮，包括默认关闭的可选实现。
- **渐变全链路属于不可删减的已有能力。**保留渐变采集、变量生成、色标绑定、填充/描边处理、共享样式与换肤联动，不得退化为只处理纯色；原型未展示不代表可以省略。
- **原型只指导界面和已确认的新增交互。**先复用正式函数和消息链；若某项新增交互必须改变上述冻结行为，应单独说明影响并重新确认，不能夹在 UI 优化中实施。

### B. 插件：新设计稿 JSON 路径

```text
粘贴 JSON
  → normalizeData（识别格式、解析别名、保留字体元数据）
  → 显示规范名称/版本/模式/数量，启用按钮
  ├─ 同步 Figma 变量
  │    → syncVariables → syncTextStyles → syncEffectStyles → 完成反馈
  └─ 生成预览页
       → syncVariables → syncTextStyles → syncEffectStyles
       → generatePreview → 定位预览 → 完成反馈
```

必须保留：

- 两个按钮相互独立；**生成预览页已经内含同步变量和样式，不能改成必须先手动同步**。
- 支持 `{seed,tokens,...}` 完整格式与 `{colorTokens,dimTokens,...}` 简化格式。
- 空内容、错误 JSON、清空、生成器版本不一致提示；处理过程中禁用按钮，成功/失败后正确恢复。
- `role/weight/lineHeight` 元数据贯通，字号来自 `tokens.js` 的单一数据源，不从原型重新造阶梯。
- 创建/更新 Primitives 与 Tokens，模式与变量作用域、字号变量原位改名、文字样式字体回退及排序、阴影效果样式。
- **opacity 数字变量 0.05 → 5、0.8 → 80**；但颜色 RGBA 的 alpha 仍是 0–1，不可混为同一种换算。
- Light/Dark 预览、字体加载与回退、预览内变量引用及显式模式。
- 反推功能的成功回包不能误启用没有合法 JSON 的导入按钮。

### C. 插件：反推现有设计稿路径

```text
选中画板/图层 + 自动/浅色/深色
  → audit：只读扫描，统计并提示已有变量库
  → rebuild：保真整理，缓存计划，展示各类 token 明细
  ├─ reverse-preview：转换为现有预览数据 → 复用 generatePreview
  ├─ reverse-bind：建库/别名 → 复制画板 → 绑定 → 定位副本
  └─ 复制重建 JSON
绑定后 → reverse-recolor：输入 HEX/拾色器 → 换主色
```

现有特点与兼容要求：

- 扫描基于当前选区，不会自动扫全文件；上限 20,000 节点，有截断提示。
- 已扫描颜色、字体家族/样式、字号、圆角、阴影、Auto Layout 间距与内边距；已处理部分混合文本分段。
- 已有色块、近似色对、字号/圆角/间距数值清单和整理后 token 明细，不应重做后反而只剩统计数。
- 审计近似色阈值默认 2.5；真正重建默认 `colorDelta=1.0`。两者目的不同，不可因为界面同叫“整理”就统一阈值。
- 字号保留不同整数值；圆角保留不同整数值，但已有 `>=100` 合并为 `radius.full` 的规则；间距整数原样保留，不自动吸附网格。小数尺寸用取整规则。
- 阴影有扫描/整理明细；**反推绑定当前保留图层特效，不自动生成反推阴影样式**。不能与正向 JSON 路径的阴影样式同步混淆。
- 明暗检测看非文本、非渐变色标填充的面积与透明度加权，不是简单读取 Page 背景；已有手动覆盖，必须保留。
- 反推预览复用现有生成器，但不像正向 `generate` 那样先同步变量；现有变量环境会影响预览绑定，需分别验收。
- 当前设计稿复制与其中的组件复制沿用已有实现，按用户确认纳入兼容基线；不新增公共组件库母版复制流程。
- 绑定保留颜色透明度、渐变色标和填充栈，区分背景/描边/文本语义，处理本地颜色样式与渐变样式提升。
- 渐变填充和描边的色标均进入采集；已有色标变量绑定、匹配限制、未匹配原色保留、整组 paint 样式提升及换肤联动，详见 4.7，全部作为已有能力保护。
- 文字填充先加载字体再绑定；多色文本按分段处理；图片/视频及不能处理的特效有保留统计。
- 反推 Primitives 收为单模式，Tokens 保留 Light/Dark；不能把这一反推行为套到正向 JSON 同步。
- 换肤使用 OKLCH、动态档数与原主色锚点，除了主色阶还处理其他色族中的同色相品牌色，并保护功能色引用。
- 换主色是已有独立入口，运行过绑定后可继续用；重置反推面板也保留该入口。新导航不能要求每次重开插件都重跑前四步。
- 整理后预览与绑定是并列操作，绑定不以“已经生成预览页”为现有技术前提。五步导航可引导，但不应无声删除原有快捷路径。
- “复制重建 JSON”是已有独立交付入口；其 `{color,font,...,$meta}` 结构不是上方 `normalizeData` 支持的两种格式，不应宣传为已支持直接粘回。

## 4. 最需要保护的技术边界

### 4.1 原稿安全不能只看是否 clone 画板

`syncVariables` 按文件级同名变量查找，`bindPaintStyles` 修改文件已有本地颜色样式，`aliasReverseSemantics` 与换肤也进行文件级变量查找。因此，如果原稿或其他设计稿引用同一组资源，复制画板不代表依赖已经隔离。

依据：[文件级变量索引](/Users/shirley/Documents/design-system-generator-v2/figma-plugin/code.js:120)、[全文件本地样式写入](/Users/shirley/Documents/design-system-generator-v2/figma-plugin/code.js:2379)、[反推语义别名](/Users/shirley/Documents/design-system-generator-v2/figma-plugin/code.js:2193)。

计划：新增副本选择能力需明确本次输出的变量集合/样式 IDs，更新模式只操作明确属于选定副本的资源。旧文件不能仅凭集合名字认定归属。未知归属保留并提示，不能默认迁移、覆盖或删除。

这里讨论的是共享变量/样式的写入边界，**不是重新开发当前设计稿的组件复制**。组件复制继续沿用现有实现。若隔离资源需要改变现有渐变样式共享范围等行为，先列出受影响对象、旧版结果和替代方案供确认；本轮不能据此删掉样式绑定或重写保真算法，未确认的扩展暂缓上线。

### 4.2 副本更新是有意的能力扩展

当前代码会删除名为「反推规范 · 绑定副本」的页面，现有测试也明确覆盖“只留最新副本页”。真正保留旧副本或原位更新，与这个行为不同，不能只替换 UI 文案。

依据：[同名页清理](/Users/shirley/Documents/design-system-generator-v2/figma-plugin/code.js:2314)、[现有回归断言](/Users/shirley/Documents/design-system-generator-v2/tests/binding-tests.js:206)。

新规则仍按最后确认的原型：首次绑定创建副本；后续保留“更新已有副本/新建另一份副本”。新建不影响既有副本；更新要维护节点/变量身份并处理用户后续编辑冲突，不能通过删除重建伪装成更新。失败重试不等于新一轮绑定。

### 4.3 旧变量保留不是简单取消一个确认框

现有 `syncVariables` 会清理 iOS 前缀变量及受管理命名空间的 orphan；另有经确认整库清理 Primitives/Tokens 的入口。其归属判定较粗，不能把 UI 上的“保留”与底层仍在自动清理并存。

依据：[旧变量与全文件 iOS 清理](/Users/shirley/Documents/design-system-generator-v2/figma-plugin/code.js:106)、[orphan 清理](/Users/shirley/Documents/design-system-generator-v2/figma-plugin/code.js:272)、[整库清理消息](/Users/shirley/Documents/design-system-generator-v2/figma-plugin/code.js:2608)。

计划：先给原有默认行为补测试；新增反推执行上下文与删除策略，不静默改变正向 JSON 同步。删除仅来自已确认的精确清单，纳入依赖检查；同名但无法证明归属的变量不删除。高风险整库清理不在 UI 优化阶段随手移除或重用为新 Diff 的“删除”。

### 4.4 扫描范围与导航选区必须解耦

当前缓存只有 `lastRebuildPlan`，而绑定重新读取 `figma.currentPage.selection`。新增“定位文本/颜色/圆角”后，定位本身会改变选区；若不保存扫描范围，后续绑定可能拿旧计划处理新选区。

计划：保存扫描会话的源页面、去重后的根节点 IDs、源数据版本、问题定位索引；定位不会改写会话范围。用户确实更改扫描范围时要求重新扫描。跨页、节点删除、文件内容变化时使受影响计划失效，不能沿用旧计数假装完成。

### 4.5 两条模式逻辑不能互相覆盖

正向：Primitives/Tokens 的 Light/Dark 与 Web 导出一致。反推：Primitives 单值、语义色对侧模式推导、副本显式模式。新界面共用“预览”按钮，不意味着可以无差别调用同一种同步顺序。

### 4.6 单元测试通过不等于完整安全验收
